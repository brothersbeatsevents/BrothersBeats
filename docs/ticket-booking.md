# Child tickets and mixed bookings

In Admin → Events, open the event and choose **Add ticket type → Child**. The form starts with the name “Child 0–12 yrs” and a price of €0. Set the age label, description, capacity and sales dates to suit the event. Edit updates the name, description, price, capacity and dates; Hide stops public selection. A type with sales or reservations cannot be deleted.

Every free child admission creates an individual ticket with a QR code and PDF. It counts toward event capacity, ticket totals and attendance, with its own row in sales reports. A booking containing only free tickets confirms immediately without Stripe. A booking containing paid and free tickets uses one Stripe checkout and issues all tickets after payment confirmation.

Customers and admins making manual bookings can select multiple ticket types in one booking. Public checkout enforces each type’s limits, the Group minimum, and the event’s combined per-order limit and capacity. Early Bird remains an automatic discount on Standard tickets.

After selecting tickets and clicking **Next**, signed-out visitors can **Sign in**, **Sign up**, or **Continue as guest** when the event permits guest checkout. The selected ticket types and quantities stay in the checkout URL through sign-in, account verification, Google sign-in, and password reset. Signed-in customers proceed directly to their booking details.

Event details use uncached availability. The ticket selector refreshes counts every 30 seconds while visible, when visitors return to the tab, and after a failed price check. Counts respect both ticket-type and event capacity. If another booking reduces stock, the selector retains the visitor's selection and shows the current count so they can adjust it.

Online, free, and manual bookings send one confirmation email after tickets are generated. It includes the booking summary, every ticket number and type, each ticket PDF as an attachment, and a **View & Download Tickets** link. Customers can save or print the attachments directly from their email. There is no separate automatic ticket-delivery email. Requested resends still send one email per request; both confirmation and ticket resends attach every ticket PDF. Missing or unreadable PDFs fail the send and report an error on resend rather than sending an incomplete email.

Paid checkout reserves tickets for 15 minutes. Stripe's automatic session expiry remains at its 30-minute minimum; an EventBridge job runs every minute to manually close unpaid sessions once the reservation deadline has passed. New checkout requests run the same cleanup for their event. Inventory is returned only after Stripe confirms the session is expired, and the booking and inventory updates occur atomically so overlapping jobs and webhooks do not release the same tickets twice. Completed sessions retain their inventory for payment fulfillment; Stripe errors retain the reservation and are retried. Deploy the backend SAM template as well as the application code to enable the scheduled cleanup.

Guest bookings never require an account to retrieve tickets. Paid and free checkout return to a public ticket page, and confirmation/resend emails link directly to that page with a secure bearer token. It shows each ticket's QR code and PDF download. Payment confirmation and ticket generation refresh automatically for up to 30 seconds after checkout. **Find my ticket** in the navigation and footer offers **Booked with an account** (sign in and open My tickets) and **Booked as a guest** (enter the booking email and optional reference). Confirmed guest bookings receive ticket PDFs and a fresh secure ticket link by email; other booking statuses receive a link to their booking details. Recovery always gives a generic response and sends only to the booking's saved buyer email. Older `/account/tickets/{bookingReference}` links route signed-out guests directly to the guest form with their reference filled in.

Signed-in customers also see unclaimed guest bookings matching their verified account email in My tickets and the account overview. The same access rule covers ticket detail, PDF downloads and resend. Matching requires the identity provider's verified-email claim; another email or a booking already linked to another account cannot grant access. Displaying a guest booking does not transfer its ownership. Account loading failures show a retry action instead of incorrectly displaying “No bookings yet”.

Ticket links use 32 random bytes; only SHA-256 token hashes are stored under `BOOKING_ACCESS_TOKEN` in the existing DynamoDB table, with TTL cleanup and expiry checked on every request. Email and checkout links expire a week after the event starts (or a week after issuance for past events); lookup email links expire after 30 minutes. The old development-key signed links are rejected; users can request a fresh link without signing in. Booking-reference-only, unknown and expired tokens cannot retrieve tickets. Booking responses are marked `private, no-store`, and booking pages disable indexing and referrers.

Email deployment uses `tickets@brothersbeatsevents.com` as the SES sender, with replies directed to `SUPPORT_EMAIL` (default `brothersbeatsevents@gmail.com`). The sender domain must be verified in SES with DKIM signing enabled in the deployment region. Sending through SES with a Gmail From address cannot authenticate as Gmail; use the verified domain instead. Both booking and ticket emails include HTML and plain text.

Publish a DMARC TXT policy at `_dmarc.brothersbeatsevents.com` (for example, `v=DMARC1; p=none` while monitoring delivery). The public DNS check on 26 October 2026 returned no DMARC record for this domain. DKIM was already verified in SES; changing the From address to this domain lets its signature align with the visible sender. See [SES DMARC authentication](https://docs.aws.amazon.com/ses/latest/dg/send-email-authentication-dmarc.html) and [Apple's iCloud postmaster guidance](https://support.apple.com/en-gb/102322).

Resend actions report success only after SES accepts the send request; this does not confirm inbox delivery. Skipped or rejected sends return an error, and failed resends do not create a success audit entry. To trace delivery, match the `[SES]` accepted message ID with `[SES-SNS]` delivery, bounce, or rejection events in CloudWatch. Bounce events include the recipient server's diagnostic response. Check both the application's `emailSuppressions` records and SES's account suppression list before retrying; do not clear complaints or hard bounces without investigating the cause.

The pricing and checkout endpoints accept `items: [{ ticketTierId, quantity }]`. Admin manual bookings accept the same shape. Existing requests with `ticketTierId` and `quantity`, and stored bookings without `lineItems`, remain supported. Prices are always calculated by the backend.

Run `npm test --prefix backend` for the regression suite. Stripe, email and S3 calls in the integration tests are mocked; tests do not make real payments or send emails.

## Discount and referral codes

In **Admin → Discount codes**, select an event, choose 5%, 10%, a custom percentage (up to 100%), or a fixed amount per ticket. Leave the code blank to generate one, or enter your own shareable code. Optionally select specific ticket types and an expiry date. Leaving all ticket types unchecked includes all types in that event. Existing codes can be enabled or disabled; create a new code to change its discount or scope.

Customers select **I have a discount or referral code** at checkout and click **Apply** to see the savings and updated total before payment. They can remove the code to return to regular pricing. Codes ignore letter case and surrounding spaces, and one code applies per booking. They can be shared with multiple customers and have no redemption limit or referral payout.

Discounts apply to each eligible ticket's current price, including its automatic Early Bird price. Percentage savings are rounded to the nearest minor currency unit per ticket. Fixed discounts are capped at each ticket's price, so free tickets stay free. A fully discounted booking confirms immediately and issues tickets without Stripe. Bookings retain the code, savings and discounted line amounts; sales reports and refunds use the amount actually charged.

`POST /api/admin/discount-codes` accepts `eventId`, optional `code`, optional `ticketTierIds` (an empty array means all), `discountType` (`PERCENTAGE` or `FIXED`), `value`, and optional ISO `expiresAt`. Percentage values allow two decimals; fixed values are integer minor currency units (500 means €5 for EUR tickets). `GET /api/admin/discount-codes` lists codes; `PATCH /api/admin/discount-codes/:code` accepts `{ active: boolean }`. These routes require admin authentication and record changes in the audit log. Codes are stored in the existing DynamoDB table, with an atomic uniqueness check and no table migration.

Both `POST /api/pricing/quote` and `POST /api/checkout/session` accept optional `discountCode`. Checkout revalidates eligibility, expiry and availability and recalculates all prices on the server before reserving inventory. Quotes expose `discountCode`, `discountAmountMinor`, the original subtotal and discounted total. Invalid, expired, disabled, wrong-event or non-applicable codes return a validation error.
